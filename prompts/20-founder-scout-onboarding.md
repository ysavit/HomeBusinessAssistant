## Goal

Provide a specialized, resumable Founder Scout setup wizard that safely configures its typed settings, verifies local browser and optional AI prerequisites, launches only explicit headed authentication through Runner, and leaves the agent disabled until Stage 22 validation/activation.

The flow is:

```text
Purpose and privacy
  -> browser account
  -> discovery source and limits
  -> screening/fit policy
  -> AI provider and protected key
  -> browser/provider checks
  -> review configuration
  -> Ready for diagnostic (Stage 22)
```

Invitation sending remains manual. This wizard must not add a send API or imply that live Startup School automation is guaranteed.

## 1. Specialized adapter

Implement an explicit `FounderScoutOnboardingAdapter` behind the Stage 19 contract. Reuse `FounderScoutConfiguration`, its validator/default provider, configuration revision service, browser-account/segment application services, secret store, and existing Runner dispatch boundary.

Requirements:

- adapter version and stable step keys;
- typed load/save mapping without exposing EF entities;
- preserve unknown forward-compatible values according to existing typed configuration rules;
- save through authoritative validation and immutable configuration revisions;
- never copy full configuration JSON into onboarding persistence;
- store only final revision ID/hash and safe check/result references;
- existing Agent Settings and Founder Scout Operations remain authoritative after onboarding.

## 2. Purpose, consent, and privacy step

Explain in concise UI copy:

- Founder Scout uses a dedicated persistent browser profile under the local data root;
- authentication is completed manually in a headed browser;
- passwords, cookies, and browser authentication payloads are not stored in configuration or ordinary backup;
- external navigation requires HTTPS and expected hosts;
- discovery stops on login redirect, access denial, throttling, challenge/CAPTCHA, or parser-health failure;
- protected/irrelevant personal attributes are excluded from evaluation;
- AI output is validated and arithmetic is calculated in C#;
- drafts and queues are for human review; no invitation/message is sent automatically;
- live operation must comply with the source site's terms and the user's authorization.

Require an acknowledgment before live browser setup, but allow fixture-only/local evaluation setup without pretending live consent occurred.

## 3. Browser account step

Provide a typed form for one initial browser account and safe extension to multiple accounts:

- account ID and display name with strict bounded identifiers;
- enabled state for the account, default false until authentication succeeds;
- canonical browser-profile relative path generated by the platform, never an arbitrary absolute path;
- safe authenticated locator strategy selection from code-owned defaults;
- optional source-segment assignment;
- no password, cookie, storage-state, or proxy credential fields.

Account creation/update must use existing Founder Scout application services and audit. Do not create the browser directory on a simple GET. If an existing account is selected, show status and safe relative identifier only; do not expose a full user path.

## 4. Discovery source and limits step

Configure one small initial source segment:

- stable segment ID/name;
- expected Startup School HTTPS start URL/route through an allow-listed typed control;
- account assignment;
- maximum pages/profiles per run;
- cooldown/fixed-delay preference metadata for Stage 22;
- parser-health threshold and raw retention choice;
- optional safe filters supported by the existing adapter.

Use conservative defaults suitable for a first live pilot. Do not expose arbitrary JavaScript, selector code, proxy rotation, stealth, human-movement randomization, CAPTCHA solving, automatic account failover, or unrestricted URLs.

Show a strong warning when raw HTML retention is enabled. Photographs remain excluded.

## 5. Screening, fit, and invitation-policy step

Reuse the typed Founder Scout configuration for:

- deterministic screening thresholds;
- founder quality versus local persona fit;
- invitation priority policy;
- primary/reserve queue capacities;
- activity and risk policy;
- short/detailed draft constraints;
- retention.

Use platform-owned labels/help. Do not ask for protected attributes and do not allow them to be weighted. Persona text is sensitive local configuration: validate/bound it, never log it, never add it to onboarding check rows, and show it only on its authorized edit form.

Provide safe defaults and an advanced section. The user can change all settings later under Agent Settings without rerunning the whole first-run workflow.

## 6. AI provider and API-key step

Support the existing production providers only:

- OpenAI Responses API;
- Azure OpenAI v1 Responses-compatible endpoint.

Configure provider, endpoint, model/deployment, timeout, output limits, prompt/scorecard version, and opaque API-key secret reference through typed controls. Keep `DiagnosticFake` available only in development/test mode with an unmistakable label.

Secret requirements:

- API-key input is a separate password mutation;
- never prepopulate or redisplay it;
- show existence and last safe validation time/status only;
- store with `ISecretStore` under the current Windows user;
- deleting/replacing it is separately audited;
- no key in configuration JSON, onboarding state, ModelState, query strings, logs, diagnostics, or protocol events.

### Explicit provider check

Add an optional user-triggered `Test provider` operation through an Application/Infrastructure port, not inside the Razor Page.

- First validate endpoint/model/secret existence locally.
- Clearly state that the test makes a network request and may incur a small provider charge.
- Use the existing official OpenAI client adapter and a minimal strict structured request with no founder/persona/profile content.
- Apply a short timeout and cancellation.
- Classify invalid credential, forbidden/deployment-not-found, quota/rate-limit, network/TLS, malformed response, and success with stable safe reason codes.
- Persist only provider kind, endpoint host or hashed normalized endpoint as already allowed, model identifier if safe, timestamps, latency bucket, and result code. Never persist the request/response body or key.
- Do not automatically retry chargeable tests.
- Normal tests use a loopback fake handler and never contact OpenAI/Azure.

Provider readiness is required only for deep analysis. The user may select capture/screen-only mode and defer AI setup.

## 7. Browser runtime and authentication checks

### Browser runtime

Check the pinned Playwright package/runtime revision without downloading anything on GET.

- Report installed/missing/version mismatch with safe paths omitted.
- Provide the existing reviewed repair command/instructions.
- An explicit Install action, if implemented, requires confirmation, progress, cancellation, bounded logs, and clear network/disk impact; otherwise link to the repair workflow.
- Browser missing blocks live authenticate/discover but not fixture-only configuration or no-AI screening.

### Headed authentication

The `Authenticate interactively` action must:

- require explicit confirmation and an interactive current-user session;
- create a durable manual occurrence for Founder Scout `authenticate` with the selected account ID;
- dispatch only through Runner;
- open the headed browser from the agent process;
- show persisted run progress/status by polling;
- never ask the user to enter credentials into the Home Business Assistant UI;
- stop safely on cancellation, unexpected host, challenge, access denial, or timeout;
- update account session status through existing Founder Scout persistence;
- show `Authenticated`, `Authentication required`, `Challenge detected`, `Access denied`, `Timed out`, or `Unknown` without cookies/session details.

Do not automatically run discovery after authentication.
