## Runtime and security state

- Host is the loopback-only, single-instance interactive composition root. Founder Scout simple mode removes browser Negotiate authentication and therefore trusts local workstation processes able to reach loopback; exact binding/Host/Origin, CSP, antiforgery, and no-CORS controls remain. Its STA application context owns the tray, Kestrel, four hosted loops, current-user-only per-user/session activation pipe, manual power state, and shutdown ordering.
- Runner is the authoritative durable occurrence executor and recovery process. Wake Remote is an independently executable operational agent. Founder Scout is independently executable for fixture import/reporting, browser/account diagnostics, headed manual authentication, bounded persistent-profile discovery, deterministic parsing/redaction/screening, and structured cached deep evaluation with human-review-only drafts.
- Agent installation is a contained external-process package workflow. The registry scanner inspects at most 128 immediate non-reparse directories, requires exact folder/manifest identity plus schema/executable, hashes the executable, registers new agents disabled, preserves user state on update/removal, and audits invalid/removed packages. It never loads discovered code into Host or Runner.
- `templates/hba-agent` is the supported repository-local scaffold. `agents/SampleBusinessAgent` is a harmless local-folder report reference agent and is excluded from default production packaging unless `-IncludeSampleAgent` is explicit.
- No persistent repository database, secret, Task Scheduler task, wake request, backup, browser profile, or runtime log was created by Stage 16 validation. The ignored final RC and synthetic UI screenshots are retained under `artifacts/stage16-release` and `artifacts/stage16-ui-qa`; the Unicode/space install/data root was removed after uninstall. The installed Playwright browser revision remains in the user cache as an explicit prerequisite. Browser/provider/evaluation checks used loopback/synthetic data and the labeled deterministic fake; the live AI test remained opt-in. Real power requests were bounded and released, and no machine-global wake task was changed.
- DPAPI `CurrentUser` protects secret files at rest from casual inspection and other Windows users, but code already executing as the same Windows user can unprotect them. Secret files are intentionally non-portable and excluded from ordinary database backup scope.
- `.gitignore` covers build/IDE output, local .NET/NuGet caches, databases/WAL files, logs, browser profiles, snapshots, screenshots, reports, backups, secrets, temporary execution inputs, and published output.
- Host tests verify anonymous health, owner-only management routes, exact loopback/Host/Origin policy, real ephemeral Kestrel pages, secret/diagnostics exclusions, CSP, encoded hostile output, responsive landmarks/focus/overflow, and antiforgery rejection for state-changing handlers.

## Known limitations and manual prerequisites

- The repository began as an untracked prompt pack, so all prompt-pack and Stage 00 files remain untracked. No Git commit, branch, tag, or pull request was requested or created.
- Native tray icon visibility, taskbar notification appearance, real second-launch dashboard focus, and interactive exit confirmation require the documented manual Windows smoke; automated coverage validates the controller, actual mutex/pipe transport, Kestrel, power boundary, and cleanup paths without GUI automation. That manual UI smoke was not performed in this non-interactive run.
- Founder Scout browser discovery/authentication and deterministic processing are validated against both production-shaped fixtures and live authenticated Startup School runs. The current local database contains 20 visible real candidate profiles from the final run, all deterministically screened with zero pending. Two historical navigation-page rows from the superseded adapter remain in the database for auditability but are excluded from candidate views and counts. Live OpenAI/Azure evaluation remains opt-in and was not used; no provider credential or charge was involved.
- Newly installed agents are discovered only when `scan-agents` runs (installer/repair/smoke invoke it); no file watcher or automatic execution exists. A newly registered agent remains disabled until the owner explicitly configures and enables it.
- Package discovery validates containment, schema/manifest shape, executable presence/size/hash, and exact identity, but it does not establish publisher trust or sandbox an explicitly installed executable. Agent packages remain unsigned and execute with the current Windows user's authority.
- Generic configuration deliberately supports a safe subset only: primitive values, enum, simple arrays, and opaque secret references. Nested/conditional/union/dictionary schemas require a code-owned typed adapter. The Stage 17 rendered-browser pass was not repeated at the user's request; server integration tests cover the generic route, encoded controls, authoritative validation, and non-echoed secret behavior.
- Stage 20 originally stopped after a confirmed Runner `authenticate` occurrence. The simple-mode increment supersedes that activation boundary: it enables Founder Scout and exposes an explicit capture-first `start` occurrence, but still creates no schedule, starts no work automatically, performs no deep AI request, and sends no invitation. A healthy session is reused; missing/stale authentication opens the official headed flow. Wake Remote setup remains Stage 21 work.
- Task Scheduler and power results are read-only capability observations, not proof of a future hardware wake. The current machine still cannot query the Task Scheduler root; onboarding reports that condition safely and provides manual-start caveats without registering/replacing tasks or changing power policy.
- Local validation used ignored `.dotnet-cli/` and `.nuget/` caches because the execution sandbox could not write normal user-profile CLI state.
- A Windows machine and the same Windows user profile are required to unprotect stored DPAPI secrets. Secret migration/recovery across users or machines requires explicit re-entry.
- Protocol 1.0 has no pause/resume or cooperative cancellation control channel. The Founder Scout Overview Stop action records a central Runner cancellation request; Stage 04 waits a grace period and then kills the entire process tree when needed. Already committed candidates remain. Recovery cannot reattach redirected streams; a plausibly matching live stale child is left running and audited until a later recovery observes it absent.
- Windows ACL restriction on temporary execution input is best-effort and Windows process path/start-time inspection can be denied; containment and ambiguous-PID recovery fail closed. Executable integrity is checked immediately before and after launch, not continuously after the process starts.
- Host loops poll persisted state in V1. Schedule, wake, recovery, and notification work is therefore bounded by configured intervals; there is no distributed push/message bus. Claims and leases prevent duplicate execution when Host and the wake task race.
- Both managed tasks use `InteractiveToken` and therefore require the same user to remain signed in. Locked/sleeping is the intended V1 case; signed-out execution is unsupported. HostAtLogon is implemented, but real registration could not be completed because this machine's running Task Scheduler service still returns path-not-found from both `schtasks` root query and COM root-folder access. The failure is bounded; no task or plaintext password was left behind.
- Wake capability depends on firmware, Modern Standby/hibernate support, Windows power policy, battery state, permissions, and wake timers. The real `/waketimers` query on this machine required elevation; a real Task Scheduler registration attempt failed as described above, and no hardware sleep/wake test was performed.
- `SetThreadExecutionState` prevents idle sleep while Runner work holds the request but does not override explicit user sleep/shutdown or unsupported platform behavior. Display-required remains opt-in and unused by current production occurrence creation paths.
- Chrome Remote Desktop/RDP readiness is a conservative local service/process/listener signal, not proof of internet reachability, authenticated access, or a successful remote session. Provider service/process names can vary by installation and are user-configurable through the Stage 08 typed local UI.
- The Stage 08 in-app browser smoke covered page loading, real schedule preview, labels, console health, desktop/narrow layout, and safe secret absence. It did not use the interactive tray to register a real wake task, sleep the machine, or exercise destructive production-data operations. Those actions remain opt-in and are documented in `docs/development.md`.
- Founder Scout candidate list/detail, manual queue, operations, reports, retention, and outcome surfaces are implemented. Live browser discovery and conservative deterministic fallback processing are verified; current unstructured production markup produces explicit missing fields and manual-review results. Paraphrase-grounding with a real model and provider/region/model compatibility remain unverified until explicit opt-in testing. Manual identity split remains deferred to a provenance-aware clone-and-reassign workflow; no automatic invitations, enrichment, reserve promotion, or scorecard self-tuning exists.
- RDP hosting requires a compatible Windows edition and independently configured Windows policy/firewall/network access. Wake Remote never enables RDP, alters firewall/router state, manages credentials, or exposes a listener publicly.
- `DiagnosticFake` is development/test-only and always labeled. Normal automated validation does not require live Chrome Remote Desktop or RDP.
- Wake Remote releases its keep-awake request and lets normal Windows idle policy resume; forced sleep and on-demand Wake-on-LAN are intentionally deferred.
- Online backup/restore is implemented and validated. Central expired-artifact/operational retention and Founder Scout raw/report retention remain separately owned; log cleanup beyond the rolling Serilog sink remains deferred.
- Optional durable schedules for daily backup/summary, retention, and diagnostics are not auto-seeded because no versioned platform-maintenance executable command exists in the current two-agent publish contract. Runner/UI operations are available; silently creating unexecutable schedules would violate durable scheduling guarantees.
- Authenticode signing, MSI/WiX, clean-machine SmartScreen/reputation, automatic updates, and signed release provenance remain out of scope for the unsigned folder-deployed V1 RC.
