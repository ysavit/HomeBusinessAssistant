# Stage 14 ExecPlan — Platform Audit, Summaries, and Notifications

## Purpose and user-visible outcome

Stage 14 completes the local operational feedback loop. Every terminal run receives a versioned deterministic summary, persistent conditions become deduplicated attention items, tray notifications are delivered from a durable queue, a local-day digest can be regenerated from source records, and operators can acknowledge attention, inspect health history, preview retention, apply safe cleanup, and download a bounded diagnostic archive. All delivery remains local to the interactive Windows session.

## Current repository state

- The inherited Stage 13 Release solution builds with 0 warnings and 0 errors.
- `AgentRuns` already stores optional summary text/JSON, but terminal fallback generation is distributed through Runner finalization and does not expose a stable platform schema or regeneration path.
- The Host polls recent failed runs into an in-memory `HashSet` and publishes process-local balloon notifications. Restarting loses both deduplication and pending delivery state.
- Dashboard attention is inferred from recent failures and agent rows. There is no lifecycle, acknowledgement, occurrence count, or safe context record.
- The current diagnostics ZIP is assembled in a Razor Page and has no manifest/hash ledger. Retention is limited to individual Founder Scout raw-artifact actions.

## Scope and non-goals

In scope are additive central persistence for attention, local notifications, and daily summaries; deterministic run summaries; signal detection; notification quiet hours/throttling; tray delivery and validated click routes; dashboard/settings operational views; acknowledgement; retention preview/apply; and bounded diagnostics with a manifest.

Out of scope are email, SMS, mobile push, remote dashboards, automatic repair, cloud telemetry, automatic invitation sending, destructive database compaction, and Stage 15 backup execution.

## Design and data flow

```text
terminal run / host health / Founder Scout state
  -> deterministic detector
  -> AttentionItem upsert by stable dedupe key
       -> optional LocalNotification pending row
       -> tray Host accepts delivery -> delivered timestamp
       -> dashboard acknowledgement (condition remains independently active)

source runs + events + metrics + artifacts
  -> versioned RunSummary JSON + safe text
  -> local-date DailySummary JSON/text + durable history

operator maintenance request
  -> dry-run inventory with root/path/activity guards
  -> explicit apply + append-only audit
  -> bounded diagnostic ZIP with exclusions and SHA-256 manifest
```

## Decisions

- Attention acknowledgement records operator awareness; only a detector observing recovery resolves the condition.
- Dedupe keys are stable, non-secret identifiers. Repeated observations update counters and timestamps instead of creating alert storms.
- Notification delivery is recorded only after an interactive subscriber accepts the item. Quiet hours and throttling leave rows pending.
- Summary arithmetic and aggregation remain deterministic C#. Agent-provided data is treated as bounded input, redacted, and nested beneath a versioned platform envelope.
- Retention fails closed outside configured roots and skips active-run artifacts. Audit/config revision history remains conservative and is not deleted.
- Diagnostic exports are generated by an application service, never include database files or payload-bearing sensitive sources, and contain a file hash/size manifest plus explicit exclusions.

## Recovery and rollback

- The migration is additive. Existing run/audit data is not rewritten.
- Notification and attention writes are idempotent by dedupe key; a failed iteration can retry safely.
- Retention performs an inventory first, deletes only path-confined eligible files, and records partial failures without rolling unrelated deletions back.
- Diagnostic creation writes only to a temporary in-memory/archive stream and does not mutate source operational records.

## Remaining risks and follow-up

- Native Windows balloon presentation depends on an interactive tray session; headless periods intentionally retain pending notifications.
- Native balloon appearance/click behavior still needs the Stage 15 installed-tray manual smoke; automated coverage verifies acceptance semantics and exact-loopback route rejection.
- The backup health item is intentionally a Stage 15 placeholder because no backup executor exists yet.
- Stage 15 will add packaging, installation, backup/restore operations, and production operational documentation.
